Keep the answer library current. The next tender's first draft assembles itself.

Every tender answers a buyer's question set from the same underlying material: policies, accreditations, case studies, CVs, method statements, past winning answers. Today that material lives in a folder, and the answer library is whoever has been there longest. Tenderhouse makes it a system — so the question set arrives and the draft is already half written, with every reused claim traceable to where it came from.

Where this actually stands — read this first

Available today The Flowgrid OS platform this module sits on is live: the branded workspace, the cited knowledge vault your answer library would live in, and two shipped sibling modules — Groundwork and Grantwork — that already draft cited client documents from stored records.
Not yet built Tenderhouse itself is specified and costed, not written. Nothing on this page is a working screenshot or a delivery promise. We are looking for a small number of design partners to shape it before the first line of code — and to tell us where this description is wrong.

What we intend to build

  • The question set as the unit of work. Each question is tracked in its own right — required, drafting, review, final, submitted — not buried in one long document.
  • An answer library that earns its keep. Past winning answers, policies, accreditations and case studies, retrieved by relevance rather than by memory.
  • Answer-library coverage. The share of a new question set that existing material can already serve — turning "should we bid?" from a gut call into a computed one.
  • A social-value method statement grounded in your own evidence, not generic commitments.
  • A bid/no-bid scorecard and win rates by framework, buyer and value band.

The correctness problem we care most about

  • The danger is not invention — it is expiry. The realistic failure mode in bidding is a statement that was true in 2024 asserted as current in 2026: a lapsed accreditation, a departed key person, an ageing case study.
  • So every reused claim carries a citation to its source bid, and a reviewer can check whether it is still true. We treat that as a correctness requirement, not a nicety.
  • No auto-submit, ever. A missed or wrong submission is unrecoverable and contractually consequential. Draft-first is absolute.
  • Missing facts appear as [TO CONFIRM] rather than a confident guess.

Existing bid software is priced for enterprises and sold per seat to a single organisation. A bid consultancy needs the opposite shape: one branded workspace per client, each with its own answer library, none of them able to see another's. That is what Flowgrid OS already does for every other module — and it is the reason we think this belongs here rather than as another point tool.

Out of scope for a first phase

  • No portal scraping or tender discovery. Find a Tender and Contracts Finder are not ours to automate, and you already have alerts.
  • No direct submission. You submit through the buyer's portal, as you do now.
  • No automatic parsing of ITT documents into question sets in phase one — paste and manual entry first, parsing once we have seen enough real question sets to do it properly.
  • No pricing model, e-signature or post-award contract management.

We would rather ship a narrow thing that works than a broad thing that mostly does.
